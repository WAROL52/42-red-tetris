clearLines: détection des lignes + décalage de pile

Leçon 0011 · 15 min · algorithme n°5

Quand une ligne est complète, elle disparaît et tout ce qui est au-dessus tombe. C'est clearLines(). Bien qu'inconues, cette fonction est un cas d'école d'algorithme de compaction de tableau — on y opère une suppression de lignes avec déplacement de la pile restante. Deux étapes: détecter, puis compacter.

1. La règle de jeu

  • Une ligne est « complète » si toutes ses 10 cases sont non-null (garbage compris).
  • Quand on en retire une, les lignes au-dessus descendent d'une case.
  • Le nombre supprimé (1 à 4) est reporté au serveur (linesCleared {count, spectrum}), qui envoie count-1 penalités aux adversaires.

Le moteur retourne { state, cleared } — c'est la seule fonction qui renvoie une valeur supplémentaire au GameState. Le reducer s'en sert pour construire le report réseau.

2. Étape 1 — Détection des lignes pleines

function isFullRow(board, row) {
  for (let c = 0; c < COLS; c++)
    if (board[row][c] === null) return false
  return true
}

const full = []
for (let r = BUFFER_ROWS; r < TOTAL_ROWS; r++) {
  if (isFullRow(board, r)) full.push(r)    // collecte les indices pleins
}
if (full.length === 0) return { state, cleared: 0 }
  • On parcourt du bas vers le haut en collectant les indices pleins.
  • On ne regarde que la zone visible (BUFFER_ROWS..TOTAL_ROWS) — le buffer ne produit jamais de lignes.
  • Garbage compris: une ligne X compte comme pleine… sauf qu'une ligne de garbage a toujours un trou, donc elle n'est jamais complète par elle-même. Une ligne pleine vient toujours d'une pièce qui comble le dernier trou.

3. Étape 2 — Compaction de la pile (le cœur)

Le « shift down » est l'algorithme le plus piégeux du moteur. En voici deux versions — la naïve et celle du code.

3.1 Version naive (à éviter)

// Pour chaque ligne pleine, on décale tout ce qui est au-dessus d'une case.
// Inefficace si plusieurs lignes, et bug si on le fait dans le mauvais sens.
for (const r of full) {
  for (let rr = r; rr > 0; rr--)
    board[rr] = board[rr - 1]   // ⚠️ danger si on ne copie pas d'abord
  board[0] = emptyRow
}

Traiter une ligne à la fois = O(cleared × rows). Si on traite 4 lignes en bas, on déplace très haut plusieurs fois. Et surtout, il faut faire attention à ne pas écraser des données pendant la copie.

3.2 Version compilée du code — un seul passage du bas vers le haut

const removed = new Set(full)        // indices à supprimer
const board = emptyBoard()
let shifted = 0                       // combien de lignes on "saute"
for (let r = TOTAL_ROWS - 1; r >= 0; r--) {
  if (removed.has(r)) {               // ligne retirée
    shifted++
    continue
  }
  board[r + shifted] = state.board[r] // recopie décalée vers le bas
}

Pourquoi du bas vers le haut ? Parce que chaque ligne retirée « tire » celles du haut d'une case vers le bas. En parcourant du bas, on sait toujours de combien décaler: shifted est le nombre de lignes supprimées déjà rencontrées (donc en dessous).

Exemple avec 1 ligne pleine à la 2e case (index 1, en partant du bas à 0): 

r=2: pas retirée → board[2+0] = board[2]   (décal 0)
r=1: RETIRÉE → shifted=1, on continue
r=0: pas retirée → board[0+1] = board[0]   (décal 1 → descend d'une case)
résultat: la ligne 0 atterrit en 1; la place 0 est vide.

4. Invariants & complexité

  • Un seul passage du board (les lignes ne sont déplacées qu'une fois).
  • Stable: l'ordre relatif des lignes préservées est conservé.
  • Immutable: un nouveau board est construit; l'ancien est intact.
Étape Complexité
DétectionO(rows × COLS) = O(20×10)
CompactionO(rows) = O(22)
TotalO(220) ≈ nano-par perf

C'est ce qui rend la manipulation rapide: même un Tétris (4 lignes) est géré en un seul passage, pas en 4 décalages séparés.

5. Le lien avec les tests

Les cas d'école sont couverts dans engine.test.ts:207:

  • clear simple (1 ligne), double (2), tétris (4), et zéro (aucune).
  • le test « reports zero when no line is complete » vérifie que la fonction renvoie cleared:0 et un board inchangé.
Source primaire La règle du garbage « n−1 lignes incassables » qui découle du clear est dans docs/red-tetris-spec.md §4. La logique pure (détection + compaction) est dans engine.ts:311.

6. Anticiper: pourquoi cleared est renvoyé

Regarde la signature: clearLines(state): { state, cleared }. C'est volontairement la seule fonction qui renvoie autre chose qu'un GameState. cleared alimente:

  • le report réseau (linesCleared { count }),
  • la décision de pénalité (via lastCleared dans le reducer).

Si cleared === 0, rien n'est envoyé (le reducer filtre avec if (lastCleared > 0)). C'est une optimisation d'éviter un aller-retour réseau inutile.

Mini-quiz

Dans la compaction, pourquoi parcourt-on le board du bas vers le haut ?
A. En descendant, shifted compte les lignes retirées en dessous, donc on sait toujours de combien décaler. Et comme les lignes retirées sont « sautées » (on ne les écrit pas), on n'écrase jamais une ligne non encore copiée. C'est le mécanisme de la compaction stable.
Que renvoie clearLines si aucune ligne n'est complète ?
B. { state, cleared: 0 } et le state.board retourné est le même objet que celui d'entrée (aucune copie inutile). C'est explicitement testé dans engine.test.ts:231 (expect(r.state.board).toEqual(s.board)).
