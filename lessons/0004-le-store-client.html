Le store client (useReducer + socketBridge)

Leçon 0004 · 15 min · ouvrir src/client/store/ en parallèle

Le « store » est en fait trois fichiers très petits qui se partagent le travail: un reducer pur, un adaptateur socket impur, et un provider qui les relie. Cette leçon te montre comment ils collaborent pour transformer un événement réseau en un nouveau rendu React.

1. Pourquoi useReducer et pas Redux

Le projet est de taille modeste (une seule feature, un seul écran principal). Redux serait du sur-équipement. La spec §3 a tranché pour useReducer + Context, et l' ADR 0001 documente le raisonnement. Trois bénéfices concrets:

  • Pas de dépendance (react-redux, @reduxjs/toolkit) — bundle plus léger, surface API plus petite.
  • Le reducer est la transition pure — pas de middleware à composer pour avoir un état testable.
  • Un seul fichier (reducer.ts, 227 lignes) — tu peux tout lire en une fois.

2. reducer.ts — la transition pure

Forme: (state: RootState, action: Action) => RootState. Pas de side-effects, pas de réseau, pas de Math.random(). Tout est déclaratif.

2.1 La forme de l'état

interface RootState {
  room, playerName, socketId, connected    // identité session
  status: GameStatus                       // 'waiting' | 'running' | 'finished'
  round, players, winner, eliminated       // état de la partie
  engine: GameState                        // délégation au moteur pur
  queue, currentIndex                      // file de pièces
  garbageSeed, garbageIncoming             // rng pour les garbage rows
  justLocked, lastCleared                  // flags de report
}

2.2 Les actions — deux familles

14 actions au total, réparties en deux familles:

  • Locales (3): GRAVITY_TICK, LOCAL_ACTION, REPORT_SENT — déclenchées par le clavier ou le rAF.
  • Réseau (11): SOCKET_CONNECTED, SOCKET_DISCONNECTED, ROOM_STATE, PLAYER_JOINED, PLAYER_LEFT, PLAYER_ELIMINATED, HOST_CHANGED, PLAYER_SPECTRUM, GAME_STARTED, PIECE, OPPONENT_LINES, GAME_OVER.
Le mapping 1-pour-1 Chaque ServerToClientEvent a son action Redux-like. C'est le seul travail du socketBridge : traduire « événement socket typé » en « action typée » et l'envoyer à dispatch.

3. socketBridge.ts — le seul fichier impur du store

Tout io(url, ...), socket.on(...), socket.emit(...) vit ici. C'est la seule face impure du store — tout le reste est pur et testable. Tu peux remplacer socketBridge par un mock en test, ce qui rend le reducer et le provider testables à 100 %. 

export function createSocketBridge(url, handlers) {
  const socket = io(url, { transports: ['websocket'] })
  socket.on('piece', (p) => handlers.onPiece(p))   // ...11 handlers
  return {
    emit: (event, ...args) => socket.emit(event, ...args),
    close: () => socket.disconnect(),
  }
}

Le typage est strict : emit n'accepte que des clés de ClientToServerEvents, et chaque appel a les bons paramètres TypeScript. Impossible d'émettre un événement non défini dans le protocole.

4. GameProvider.tsx — la colle

Le Provider fait trois choses en utilisant useEffect:

  1. Monter le socket au mount, brancher les 11 handlers vers dispatch, émettre join.
  2. Détecter les reports à envoyer après un lock (effet sur [state]): si justLocked, émettre lock + linesCleared si besoin.
  3. Heartbeat spectre toutes les 2 s (effet sur [state.status, state.engine.over]): ne réémet que si le spectre a changé (diff des 10 valeurs).

4.1 Pourquoi le heartbeat est gated

if (previous.length !== current.length || previous.some((v, i) => v !== current[i])) {
  bridge.emit('spectrumHeartbeat', { spectrum: current })
}

Le serveur relaie le spectre à tous les autres. Si rien n'a bougé, on s'abstient — ça évite N×N messages inutiles par seconde. C'est un trade-off explicite documenté dans la spec §4.

4.2 Pourquoi 3 useEffect séparés

  • Effet #1 (dépendances: [room, playerName, url, createBridge]) — un seul cycle de vie : mount/unmount. Le socket vit avec le composant.
  • Effet #2 (dépendances: [state]) — relit l'état après chaque dispatch pour réagir aux flags justLocked et engine.over.
  • Effet #3 (dépendances: [state.status, state.engine.over]) — le setInterval redémarre quand la phase change.

5. useStore() — l'API publique

Les composants ne touchent jamais reducer ou socketBridge directement. Ils utilisent le hook useStore() qui renvoie { state, dispatch, send }.

  • state — l'état actuel. Les composants lisent les slices qui les intéressent (BoardView lit state.engine, QueueNext lit state.queue).
  • dispatch(action) — pour les actions locales (LOCAL_ACTION, GRAVITY_TICK).
  • send(event, ...args) — pour les émissions réseau directes (par exemple send('start'), send('restart')).
Source primaire React docs — Extracting State Logic into a Reducer pour la philosophie du reducer, et l' ADR 0001 — hooks-over-redux local pour le choix appliqué à ce projet.

Mini-quiz

Combien d'useEffect contient GameProvider.tsx ?
C. Trois useEffect : mount du socket, réaction aux flags justLocked/engine.over après chaque dispatch, et interval de heartbeat spectre. Chacun a ses dépendances adaptées à son cycle de vie.
Quel fichier est impur dans src/client/store/ ?
B (et C par nature). socketBridge.ts est explicitement marqué « impure adapter » et c'est le seul fichier qui appelle io(). GameProvider.tsx est impur lui aussi (effets React), mais il ne touche pas directement à socket.io : il passe par le bridge.
