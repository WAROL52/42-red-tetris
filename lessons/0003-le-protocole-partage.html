Le protocole partagé (src/shared/)

Leçon 0003 · 12 min · lire src/shared/protocol.ts en parallèle

Le dossier src/shared/ contient deux fichiers seulement: protocol.ts et validation.ts. Ces deux fichiers sont importés par les deux tsconfig du projet — celui du navigateur et celui de Node. C'est la seule zone d'intersection entre client et serveur, et c'est volontaire: ça force les deux côtés à parler exactement la même langue, sans rien d'autre en commun.

1. protocol.ts — le dictionnaire des messages

Le fichier ne contient que des type, des interface et des const (pas de fonctions, pas de logique). Trois blocs à connaître:

1.1 Les types fondamentaux

export type PieceKind = 'I' | 'O' | 'T' | 'S' | 'Z' | 'J' | 'L'
export type MoveAction = 'left' | 'right' | 'rotate' | 'down' | 'harddrop'
export type GameStatus = 'waiting' | 'running' | 'finished'

export const HORIZON_LENGTH = 3

HORIZON_LENGTH = 3 veut dire: à chaque distribution de pièce, le serveur envoie aussi les 3 prochaines. Le client les affiche dans le panneau « Prochaines pièces ».

1.2 PlayerPublic — la forme publique d'un joueur

interface PlayerPublic {
  id: string           // socket id — sert de clé React
  name: string
  isHost: boolean
  eliminated: boolean
  spectrum: number[]   // 10 hauteurs
}

C'est ce qu'un client voit des autres joueurs. Pas de socketId/connected séparé: le socket id a été retiré lors du grilling du ticket 04 (cf. map). Un seul identifiant, plus simple.

1.3 Les deux dictionnaires d'événements

C'est la partie la plus importante. Deux interfaces symétriques: 

ClientToServerEvents {
  join:        ({ room, playerName }) => void
  leave:       () => void
  start:       () => void
  restart:     () => void
  move:        ({ action }) => void       // unused client-side
  lock:        ({ spectrum }) => void
  linesCleared:({ count, spectrum }) => void
  spectrumHeartbeat: ({ spectrum }) => void
  topOut:      () => void
}

ServerToClientEvents {
  state, playerJoined, playerLeft, playerEliminated,
  host, gameStarted, piece, spectrum, penalty,
  gameOver, error
}

Cette double interface est déclarée dans socket.ts comme Server — TypeScript sait alors, côté serveur, que socket.emit('piece', ...) existe et que socket.on('move', ...) attend un { action: MoveAction }. Plus de chaînes magiques lâches dans le vide.

Le contrat réseau est dans ces types. Si tu ajoutes un événement, il faut l'ajouter ici avant de l'utiliser côté code. Si tu changes le payload d'un événement existant, les deux côtés cassent à la compilation — c'est le but.

2. validation.ts — le videur

Pas de logique métier. Juste des gardes qu'on appelle avant de traiter un message reçu. Ça empêche un client malveillant (ou bogué) d'envoyer spectrum: [-5, 9999, ...] et de faire planter le serveur. 

export const NAME_PATTERN = /^[\w-]{1,24}$/   // 1 à 24 alphanum ou tiret
export const FIELD_WIDTH = 10
export const MIN_HEIGHT = 0
export const MAX_HEIGHT = 20
export const MIN_CLEAR_COUNT = 1
export const MAX_CLEAR_COUNT = 4   // Tetris = 4 max

export function isValidName(value): boolean
export function isValidSpectrum(spectrum): boolean
export function isValidClearCount(count): boolean
export function isValidAction(action): action is MoveAction  // narrowing TS
export function isValidPiece(type): type is PieceKind       // narrowing TS
export function isValidHorizon(queue): boolean

Les deux fonctions avec : type is MoveAction / : type is PieceKind sont des type predicates TypeScript: elles affinent le type après le check, donc le compilateur sait que action est bien un MoveAction dans le bloc suivant.

3. La double vie de la validation

validation.ts est importé à deux endroits:

  • Serveur (socket.ts) — il filtre les messages avant de toucher au domaine. Si !isValidSpectrum(spectrum), on jette.
  • Client — quand le client navigue vers /room/player, il appelle validateJoin avant même d'émettre le join, pour économiser un aller-retour si le nom est mal formé.
Source primaire Socket.IO — Server API pour comprendre comment Server type les émissions et réceptions.

4. La règle des imports: import type

Tu verras dans le projet import type { PieceKind } from '../shared/protocol.ts' partout. C'est parce que le tsconfig est en mode verbatimModuleSyntax : il faut être explicite entre « je veux juste le type » (pas de bundle) et « je veux la valeur » (à bundler).

Conséquence pratique : si tu modifies un interface dans protocol.ts, l'erreur de compilation apparaîtra à la fois dans src/server/ et src/client/. C'est ton garde-fou.

5. Mini-tableau de référence rapide

Mini-quiz

Combien de fichiers contient src/shared/ ?
B. Exactement deux. Pas de index.ts — les imports sont explicites (from '../shared/protocol.ts') pour rester compatibles avec verbatimModuleSyntax et garder la trace des fichiers.
Que contient protocol.ts ?
B. Pas de logique dans protocol.ts. Le code vit dans validation.ts (gardes) et dans les modules métier. Cette séparation force protocol.ts à être un contrat purement déclaratif.
