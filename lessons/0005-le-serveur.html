Le serveur (domain.ts + socket.ts)

Leçon 0005 · 15 min · ouvrir src/server/ en parallèle

Le serveur a une structure exactement inverse du client. Là où le client est fonctionnel (fonctions pures + reducer), le serveur est objet : deux classes Player et Game qui utilisent this (c'est l'un des seuls endroits où c'est autorisé — la spec l'impose).

1. Pourquoi des prototypes côté serveur

Le sujet dit textuellement: « server OOP via prototypes (Player, Piece, Game classes) ». C'est l'endroit où on accepte le this, parce qu'on muté délibérément l'état du jeu. Cette mutation est encapsulée derrière des méthodes (addPlayer, start, topOut) qui sont les seules à toucher aux champs.

Asymétrie volontaire Client = pur (immutable, testable sans React). Serveur = OOP (mutable, state machine de la partie). Le pont entre les deux, c'est le protocole.

2. Player — un humain connecté

class Player {
  readonly name: string
  readonly socketId: string
  isHost: boolean              // mutable
  eliminated: boolean          // mutable
  spectrum: number[]           // mutable (dernier spectre reçu)
  nextIndex: number            // mutable (position dans la séquence partagée)

  constructor(name, socketId, isHost = false) { /* ... */ }
}

Les champs mutables sont quatre. Tout le reste est figé à la création.

  • isHost — bascule quand l'host quitte (réélection).
  • eliminated — passe à true après topOut, remis à false à chaque nouveau round.
  • spectrum — la dernière valeur reçue via lock/linesCleared/spectrumHeartbeat.
  • nextIndex — sa position dans la séquence de pièces 7-bag. Avance quand pieceFor() est appelé.

3. Game — la room

Game est une machine à états très lisible. Voici les transitions:

État waiting

players.add() admis start() → running hostId ≠ null

État running

join() refusé pieceFor() actif topOut() → eliminated aliveCount ≤ 1 → finished

État finished

join() réadmis restart() → running round++ players.reset()

3.1 Le compteur round

round s'incrémente à chaque beginRound(). Il sert principalement à invalider les caches côté client (par exemple useEffect([round])) quand la partie redémarre.

3.2 La séquence partagée (7-bag)

private sequence: PieceKind[]
private ensureSequence(length: number): void {
  while (this.sequence.length < length) {
    this.sequence.push(...shuffle(BAG))   // mélange Fisher-Yates
  }
}

Chaque joueur a son nextIndex propre, mais tout le monde consomme la même sequence. Résultat : Alice à l'index 7 et Bob à l'index 12 reçoivent rigoureusement les mêmes pièces 8, 9, 10, …

Le mélange utilise Math.random() — donc le serveur n'est pas déterministe par défaut. C'est volontaire (le serveur n'a pas à être testé au pixel près), mais ça interdit un test « bit-exact » des pièces sans stub.

3.3 La règle unifiée de fin de manche

Deux endroits seulement déclenchent finished + gameOver:

  • Game.topOut(socketId) — quand un joueur se tue.
  • removePlayer() dans socket.ts — quand un joueur part en pleine manche (si son départ fait passer aliveCount à ≤ 1).

Cette unification (introduite au ticket 06 de la map) corrige un bug historique du squelette où le départ d'un joueur en cours de manche n'arrêtait pas la partie.

4. socket.ts — l'aiguillage

Le fichier socket.ts est fin: il ne contient pas de logique métier, juste le câblage entre événements socket et méthodes du domaine. Pattern récurrent: 

socket.on('topOut', () => {
  const game = requireGame(socket.id)
  const player = currentPlayer(game, socket.id)
  if (game === null || game.status !== 'running' || player === undefined || player.eliminated) {
    return   // no-op silencieux
  }
  io.to(game.room).emit('playerEliminated', { playerName: player.name })
  const result = game.topOut(socket.id)
  if (result !== null) {
    io.to(game.room).emit('gameOver', { winner: result.winner })
    io.to(game.room).emit('state', roomState(game))
  }
})

Trois étapes systématiques:

  1. Résoudre le contexte (requireGame + currentPlayer).
  2. Valider l'état (phase correcte, joueur pas éliminé, payload valide via isValidSpectrum).
  3. Mutate le domaine + broadcaster.

5. Le multi-salles et le nettoyage

const games = new Map()

// Quand le dernier joueur part :
if (game.playerCount() === 0) {
  io.in(game.room).disconnectSockets()
  games.delete(game.room)
}

Chaque nom de room est une clé du Map. Une room vide est immédiatement supprimée, donc les parties orphelines ne s'accumulent pas en mémoire. C'est la solution « multi-salles concurrentes » du sujet.

6. removePlayer — le cas special

removePlayer est la seule fonction qui n'est pas un handler direct — elle est appelée depuis leave et disconnect. Elle cumule quatre responsabilités:

  1. Retire le joueur du Game.players.
  2. Réélit un host si nécessaire (Game.removePlayer).
  3. Supprime la room si elle devient vide.
  4. Si la manche est running et qu'il ne reste qu'un survivant, termine la manche.
Source primaire Socket.IO — Rooms pour comprendre socket.join(), io.to(room).emit(), socket.to(room).emit() (broadcast sauf à l'émetteur) et io.in(room).disconnectSockets().

7. Anti-patterns à éviter côté serveur

  • Ne pas accumuler de pénalités. Le squelette avait Player.penalty/queuePenalty — c'est supprimé (cf. spec §4). Le serveur relaye penalty {lines}, il ne stocke pas.
  • Ne pas valider un spectrum sans isValidSpectrum. Risque d'index out-of-bounds côté client distant.
  • Ne pas émettre gameStarted sans avoir beginRound(). Sinon la room est running sans avoir incrémenté round et les clients ne se reset pas.

Mini-quiz

Combien de classes OOP y a-t-il dans domain.ts ?
B. Le sujet mentionne Piece comme « classe » mais en pratique, Piece n'existe pas comme type runtime côté serveur — la pièce est un PieceKind (string union) et c'est le client qui gère sa position via FallingPiece. Côté serveur, on n'a besoin que de Player et Game.
Que fait Game.aliveCount() ?
B. aliveCount() compte les Player dont eliminated === false. C'est la métrique qui déclenche la fin de manche: dès qu'elle passe à ≤ 1 en cours de running, la partie passe en finished.

Micro-exercice

Ouvre domain.ts et trace manuellement ces scénarios:

  • Un joueur rejoint une room vide → que valent hostId et isHost ?
  • Ce joueur appelle start() en étant seul → quel est l'état final, et winner ?
  • Il clear 4 lignes en solo → combien de penalty sont envoyés et à qui ?

Réponses : 1) hostId = socketId, isHost = true. 2) round=1, running, winner=null au gameOver. 3) Aucun (size > 1 guard : solo → personne à pénaliser).
