Vue d'ensemble: où vit quoi

Leçon 0001 · 10 min · aucune dépendance externe à installer

Avant de lire la moindre fonction, il faut une carte. Cette leçon te donne celle du projet 42-red-tetris: où sont les pièces, qui parle à qui, et pourquoi cette découpe. À la fin, tu sauras nommer chaque dossier en une phrase et pointer du doigt le fichier à ouvrir pour un problème donné.

1. Le projet en une phrase

Un Tetris multijoueur en réseau, où chaque client simule son propre terrain localement, et où le serveur ne fait que distribuer les pièces et collecter les spectres. Le jeu est rapide, le réseau lent, donc on déplace le maximum de calcul vers le client — et le serveur devient un notaire.

Idée maîtresse Le terrain (field) et la gravité vivent uniquement sur ton écran. Le serveur n'a jamais ton plateau. Il ne sait pas où sont tes pièces.

2. Les quatre dossiers à connaître par cœur

src/client/

Le navigateur components/ BoardView, SpectrumView… engine/ engine.ts (moteur pur) seed.ts (rng) screens/ HomeScreen, GameScreen store/ reducer.ts (pure) GameProvider.tsx socketBridge.ts

src/server/

Node + Hono + socket.io domain.ts (Player, Game — OOP) socket.ts (handlers d'événements) app.ts, index.ts

src/shared/

Importé par les deux protocol.ts (types + events) validation.ts (gardes)
  • src/client/engine/ — le cœur pur (aucun effet de bord, aucun réseau, aucun DOM). C'est là que vivent les règles Tetris.
  • src/client/store/ — la mémoire de l'écran: un seul useReducer, plus un socketBridge.ts qui traduit les événements réseau en actions Redux-like.
  • src/server/ — l'autorité du round: qui est là, qui est host, qui est éliminé, quelle pièce tombe pour qui.
  • src/shared/ — la langue commune: les types des événements socket et les fonctions de validation, importés des deux côtés.

3. Qui parle à qui — la boucle d'un coup de touche

Prenons un exemple concret: tu appuies sur ←. Que se passe-t-il ?

  1. GameSession.tsx capte la touche via un listener keydown global.
  2. Il envoie { type: 'LOCAL_ACTION', payload: { action: 'left' } } au reducer.
  3. Le reducer appelle applyAction du moteur, qui retourne un nouveau GameState.
  4. React re-rend BoardView avec la pièce décalée. C'est tout.
  5. Le serveur n'est pas contacté pour ce mouvement. C'est un choix d'architecture fondamental, dicté par la spec.
Source primaire Lis React docs — useReducer et Extracting State Logic into a Reducer si le pattern « dispatch + reducer pur » est neuf pour toi. 20 minutes suffisent.

4. Quand le serveur entre en jeu

Le serveur est contacté pour trois familles d'événements seulement:

  • Structurel: join, leave, start, restart — qui est dans la salle et à quelle phase on est.
  • Distribution: le serveur décide qui reçoit quelle pièce (en garantissant que tous reçoivent la même séquence). Réponse: l'événement piece.
  • Observation: après un lock, après une ligne, ou périodiquement (toutes les 2 s), tu envoies ton spectre (10 hauteurs de colonne) au serveur, qui le relaie aux adversaires.

5. La spec, ton Nord

Le fichier docs/red-tetris-spec.md consigne toutes les décisions verrouillées. Quand tu hésites (« est-ce que le serveur doit recevoir le move ? »), la spec a la réponse. C'est l'équivalent d'un contrat — les ADR (docs/adr/) et la carte (.scratch/red-tetris/map.md) en sont les traces de discussion.

À retenir pour la suite
  • Le terrain vit chez toi (client), pas chez le serveur.
  • Le serveur est un notaire: il donne les pièces, observe les spectres, arbitre la manche.
  • src/shared/ est la seule chose que les deux mondes voient en commun.
  • Toute la spec tient dans un seul fichier à consulter avant de coder.

Mini-quiz

Où vit la gravité qui fait tomber les pièces ?
B. La gravité est une fonction pure tick() dans engine.ts, invoquée à intervalle régulier (rAF, ~500 ms) par GameSession.tsx côté navigateur. Le serveur n'a jamais la gravité — il ne connaît pas la position de tes pièces.
Quel dossier est importé par les deux tsconfig ?
C. Seuls les types et la validation sont partagés. Le code métier (engine, reducer, domain, socket) est strictement séparé entre client et serveur, pour empêcher une fuite d'API impure dans le mauvais monde.
