Machine d'états du serveur (round, host, aliveCount)

Leçon 0015 · 18 min · algorithme n°10 — la gestion de la partie côté serveur

Côté serveur, le Game est une machine à états finis. Cette leçon décompose les transitions d'état (waiting → running → finished), les décisions d'élection du host, et la règle unifiée de fin de manche. C'est l'algorithme de plus haut niveau du projet — il orchestre tout le reste.

1. La machine à trois états

waiting

- joueurs admis (join) - host défini - start() → running

running

- joins REFUSÉS - pièces distribuées - topOut → élimination

finished

- joins ré-admis - restart() → running - round++ players.reset()

GameStatus est une union (définie dans protocol.ts:5): 'waiting' | 'running' | 'finished'.

2. Les transitions de base

start(): boolean {
  if (this.status !== 'waiting') return false  // garde
  this.beginRound()
  return true
}
restart(): boolean {
  if (this.status !== 'finished') return false  // garde
  this.beginRound()
  return true
}
beginRound() {
  this.status = 'running'
  this.round += 1
  for (const p of this.players.values()) {
    p.eliminated = false    // reset
    p.nextIndex = 0
  }
}
  • start() seulement depuis waiting (appelé par le host au début).
  • restart() seulement depuis finished (appelé par le host après la fin).
  • Chaque retour false = transition invalide → le socket envoie un error.
  • beginRound() (privée) remet tous les joueurs à zéro (élimination + index de séquence) et incrémente round.
Les guards internes Chaque if (this.status !== X) return false est une garde: elle garantit qu'on ne peut pas appeler start() en plein jeu ou restart() avant la fin. C'est la protection contre les transitions invalides de la machine. La spec (issue 06) a explicitement corrigé start() de « !== running » à « === waiting » pour serrer cette garde.

3. L'élection du host

addPlayer(...) {
  const wasEmpty = this.playerCount() === 0
  const player = new Player(name, socketId, wasEmpty)   // wasEmpty → isHost
  this.players.set(socketId, player)
  if (wasEmpty) this.hostId = socketId
  return player
}

removePlayer(socketId) {
  this.players.delete(socketId)
  if (this.hostId === socketId) {                    // le host est parti
    this.hostId = this.players.keys().next().value ?? null  // prochain
    const next = this.hostId !== null ? this.players.get(this.hostId) : undefined
    if (next) next.isHost = true                     // il devient host
  }
}
  • Premier joueur d'une room vide = host (wasEmpty → isHost).
  • Réélection : si le host part, le premier restant dans l'ordre d'insertion devient host.
  • Si la room devient vide, hostId = null (et la room sera nettoyée).

L'index de réélection (players.keys().next().value) est « le premier dans l'ordre d'insertion dans le Map » — un ordre déterministe et stable. C'est une stratégie simple qui suffit ici.

4. La règle unifiée de fin de manche — aliveCount

La fin d'un round se décide par un compteur: le nombre de joueurs non-éliminés. La règle est unifiée (décision 06): que ce soit un topOut ou un départ, dès qu'il reste 1 joueur vivant (ou 0 en solo), la partie s'arrête. 

aliveCount(): number {
  return [...this.players.values()].filter((p) => !p.eliminated).length
}

topOut(socketId) {
  const p = this.players.get(socketId)
  if (!p || p.eliminated || this.status !== 'running') return null  // garde
  p.eliminated = true
  if (this.aliveCount() > 1) return null      // toujours ≥ 2 vivants
  this.status = 'finished'
  const survivor = [...this.players.values()].find((p) => !p.eliminated)
  return { winner: survivor?.name ?? null }    // solo → winner null
}

Le même aliveCount() <= 1 est vérifié dans removePlayer() (socket.ts) quand un joueur se déconnecte en pleine manche. Résultat: une seule règle gère les deux causes de finition.

5. Le winner — solo vs multi

  • Multi: le dernier non-éliminé est winner = son nom.
  • Solo: s'il n'y a qu'un seul joueur (ou que tous sont éliminés), winner = null. Le client affiche un « game over » neutre.

survivor?.name ?? null gère les deux cas d'une seule ligne: s'il n'y a aucun survivant vivant (ex: un joueur solo qui top-out), survivor est undefined → winner = null.

6. La distribution des pièces — pieceFor et la séquence

pieceFor(socketId) {
  const p = this.players.get(socketId)
  if (!p || p.eliminated) return null
  this.ensureSequence(p.nextIndex + 1 + HORIZON_LENGTH)   // pré-génère au besoin
  const current = this.sequence[p.nextIndex]              // une Piece
  p.nextIndex += 1
  return current.toPayload(this.horizonAfter(current))
}
  • Même séquence: chaque joueur lit le même tableau this.sequence, mais à son propre nextIndex.
  • Horizon: on envoie aussi les 3 prochaines pièces (HORIZON_LENGTH) pour l'affichage « next » du client.
  • Pré-génération paresseuse: ensureSequence étend la séquence (via le 7-bag) seulement si besoin — on ne génère pas 1000 pièces d'avance.
  • Piece.toPayload(next): la pièce sait se sérialiser pour le réseau, mais next est dérivé de la séquence à l'envoi et n'est jamais stocké sur l'instance.

Chaque joueur qui fait un lock déclenche un pieceFor qui lui avance son index. Deux joueurs au même index reçoivent donc la même pièce — c'est la garantie « mêmes positions/coordonnées » du sujet.

Mini-quiz

Depuis quel état peut-on appeler restart() ?
C. restart() exige status === 'finished'. C'est la garde qui empêche de « tuer » une manche en cours. start(), lui, exige waiting.
Que vaut winner quand le seul joueur d'une room top-out ?
B. survivor?.name ?? null → s'il n'y a pas de survivant vivant (solo qui top-out), survivor vaut undefined donc winner = null. C'est le signe d'un « game over » neutre.

Micro-exercice

Trace avec 3 joueurs A, B, C (A host) en running:

  • B top-out → que devient aliveCount() et status ? (aliveCount=2, toujours running.)
  • C quitte la manche → que se passe-t-il ? (A est le seul vivant; removePlayer appelle la règle `aliveCount()<=1` → finished, winner=A.)
  • Qui devient host si A était host et part après la manche ? (le premier joueur restant, B ou C.)
