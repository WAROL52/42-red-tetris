SRS wall-kicks — l'algorithme « essaie jusqu'à 5 »

Leçon 0009 · 18 min · l'algorithme le plus subtil du moteur

Une rotation naïve échoue dès qu'un mino touche un mur ou un bloc. Le Tetris standard (SRS) rend la rotation forcée en essayant une série de petits décalages (wall-kicks) pour trouver une position valide proche. C'est le cœur de la « fluidité » du jeu: sans kicks, le jeu semblerait bloqué. Cette leçon décompose l'algorithme précisément.

1. L'idée: rotation + translation combinées

Quand tu appuies sur ↑, le moteur veut passer de l'état from à l'état to = (from+1)%4. La nouvelle forme vient de SHAPES[type][to] (leçon 0008). Mais rester au même (x, y) peut faire collision. L'algorithme essaie alors une liste ordonnée de décalages (dx, dy): 

function rotate(state) {
  const p = state.piece
  if (p === null || state.over) return state
  const to = (p.state + 1) % 4                    // état CW suivant
  for (const kick of kicksFor(p.type, p.state, to)) {
    if (!collides(board, p.type, to, p.x+kick.dx, p.y+kick.dy)) {
      return { ...state, piece: { ...p, state: to, x: p.x+kick.dx, y: p.y+kick.dy } }
    }
  }
  return state                                    // aucun kick ne convient → on reste (state inchangé)
}
L'invariant central du SRS Le premier décalage de la liste qui donne une position sans collision est retenu, et on s'arrête. La liste est ordonnée par préférence: on essaie d'abord le décalage nul (0,0), puis on dégrade vers des décalages de plus en plus grands. Si aucun des 5 ne marche, la rotation est annulée (on retourne l'état inchangé).

2. La structure des tables de kicks

Les décalages dépendent de trois choses: le type de pièce, l'état de départ, et l'état d'arrivée. Le code les stocke dans des tables indexées par la transition 'from->to': 

JLSTZ_KICKS = {
  '0->1': [ {0,0}, {-1,0}, {-1,-1}, {0,2}, {-1,2} ],
  '1->2': [ {0,0}, {1,0},  {1,1},  {0,-2},{1,-2} ],
  '2->3': [ {0,0}, {1,0},  {1,-1}, {0,2}, {1,2} ],
  '3->0': [ {0,0}, {-1,0}, {-1,1}, {0,-2},{-1,-2} ],
}
I_KICKS = { '0->1': [ {0,0}, {-2,0}, {1,0}, {-2,1}, {1,-2} ], ... }

Note le stress accordé à la direction de dy: le code commente « Positive dy is DOWN here » car les tables SRS sourcées utilisent y positif vers le haut. Ici, les dy positifs vont vers le bas. C'est une convention à vérifier — l'erreur classique est d'inverser le signe de y.

2.1 Trois familles de pièces, trois traitements

Type Table utilisée Notes
II_KICKS4×4, kicks plus grands (jusqu'à ±2).
Oaucuneun seul essai factice {0,0} → pas de kick réel.
J, L, S, T, ZJLSTZ_KICKS3×3, kicks jusqu'à ±2.
 
function kicksFor(type, from, to) {
  const key = `${from}->${to}`
  if (type === 'I') return I_KICKS[key] ?? [{ dx:0, dy:0 }]
  if (type === 'O') return [{ dx:0, dy:0 }]
  return JLSTZ_KICKS[key] ?? [{ dx:0, dy:0 }]
}

3. Pourquoi 5 essais, et pourquoi cet ordre

La convention SRS fixe 5 décalages par transition (le premier étant le nul). L'ordre n'est pas arbitraire: il encode les « coups » les plus probables en premier. Pour la transition 0→1 (état spawn → rotation CW) d'une pièce J/L/S/T/Z:

  1. (0,0) — souvent la rotation passe « en l'air ».
  2. (-1,0) — décale d'un cran à gauche (le « wall-kick » du côté des spins).
  3. (-1,-1) — haut-gauche.
  4. (0,2) — deux crans vers le bas.
  5. (-1,2) — bas-gauche.

Ce sont ces tables (copiées depuis srs.md, vérifiées sur 3 sources) qui permettent les T-Spins et les rotations collées au mur.

4. Le cas « aucun kick ne marche »

Si le board est assez contraint (par ex. 2 blocs qui encadrent la pièce de chaque côté), les 5 décalages échouent. Alors l'état n'est pas modifié: la rotation est totalement annulée. Le test engine.test.ts:170 vérifie explicitement ce comportement pour une pièce J coincée. 

// engine.test.ts:170 — « leaves the piece unchanged when no kick fits »

s = rotate(s)
expect(pieceAt(s).state).toBe(before.state)   // état inchangé
expect(pieceAt(s).x).toBe(before.x)           // position inchangée

5. L'asymétrie des tables — pour aller plus loin

Regarde bien JLSTZ_KICKS['0→1'] et JLSTZ_KICKS['1→2']: ils ne sont pas des symétriques parfaits. L'asymétrie est voulue par le SRS et c'est elle qui permet des comportements spécifiques (rotation glissante vers un côté plutôt que l'autre). Le signe de dy est un piège : le SRS officiel liste les tables avec y croissant vers le haut, alors que engine.ts (et le board) utilisent y croissant vers le bas. C'est précisément pourquoi le code a un commentaire d'alerte en tête de section. Toujours convertir avant de copier une table externe.

6. Résumé algorithmique

Étape Coût Condition
Choisir table (kicksFor)O(1)type + transition
Essayer les kicks en séquenceO(5 × collision)≤ 5 itérations
Premier kick valide—early exit
Aucun kick valide—rotation annulée, état intact

Au pire, une rotation teste 5 positions × 4 minos = 20 tests de collision. C'est O(1) et négligeable à 60 fps.

Mini-quiz

Lors d'une rotation, combien de décalages essaie la pièce J en plein air ?
A. En plein air, le premier décalage (0,0) est valide dès le premier essai, donc on s'arrête immédiatement (early exit). Les 4 autres ne sont testés que si le premier échoue. L'algorithme essaie « jusqu'à 5 », pas « toujours 5 ».
Que se passe-t-il si les 5 kicks de la transition échouent ?
B. Si aucun kick ne donne une position sans collision, rotate() retourne l'état tel quel (pas de rotation). C'est vérifié par le test engine.test.ts:170: état et position restent identiques.
